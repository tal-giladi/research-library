Practical recipe for Tal’s agent fleet: re-label tool inventory by free-text field writers, rank agents by untrusted fields × state-changing tools (coding agents in remote envs sit at the top), baseline per-agent behavioral history, run audit→enforce, and keep dual-LLM / delimiter screens as volume filters—not as the control that catches a targeted payload.

### 6. Built for Reliability — Amex cell-based payments (ByteByteGo)
Primary link: https://blog.bytebytego.com/p/built-for-reliability-how-american

Ben Cane (Amex Distinguished Engineer) via ByteByteGo on cell-based payment architecture—a clean reliability parallel for multi-agent / multi-harness systems. A cell is a full self-sufficient copy of the payment stack (services + DB + DNS + supporting infra): independent deploy, single failure domain, pullable from rotation, and—critically—no synchronous cross-cell dependencies on the critical path. Cloud-native modernization since 2018 assumed servers disappear. Data locality: push/distribute immutable and semi-static reference data ahead of time (avoid cold-cache fall-throughs); for dynamic data, move the *transaction* to the cell that holds truth via deterministic routing (partner/market/payment type) through a deliberately thin Global Transaction Router that is the only cross-boundary path and carries almost no business logic. Mid-failure policy is restart-not-resume: discard partial work and reprocess from original input in a healthy cell rather than share in-flight state (a few hundred milliseconds of redo beats permanent coupling). Point-of-no-return placed late; idempotency IDs suppress duplicates; percentage canaries pace failback. Tradeoffs accepted: duplicated services, truncated logs under pressure, lagged global observability, occasional rejects for consistency. Mapping for agent platforms: treat each agent runtime/cell as an isolation boundary, keep the router/orchestrator thin, prefer restart-with-idempotency over checkpointed shared state across failure domains, and push reference/skill context rather than synchronous cross-cell fetches on the hot path.

## Skills / agent memory

### 7. SkillOpt — agent skills as trainable parameters (Microsoft; Tal X forward)
Primary link: https://www.microsoft.com/en-us/research/blog/skillopt-agent-skills-as-trainable-parameters/
Also: https://arxiv.org/abs/2605.23904 · https://github.com/microsoft/SkillOpt · https://x.com/omarsar0/status/2062204469538881988

Microsoft Research’s SkillOpt reframes skill writing as training: a frozen target agent runs tasks while a separate optimizer proposes bounded add/delete/replace edits to a natural-language skill document; edits are accepted only if they strictly improve a held-out validation score, with textual learning-rate budgets, rejected-edit buffers, and epoch-wise slow/meta updates—zero extra model calls at deploy time. Across six benchmarks × seven models × three harnesses (direct chat, Codex, Claude Code), SkillOpt is best or tied-best on all 52 cells; on GPT-5.5 it lifts average no-skill accuracy by +23.5 (chat), +24.8 (Codex), +19.1 (Claude Code), with huge procedural jumps (e.g. SpreadsheetBench 41.8→80.7). Optimized `best_skill.md` artifacts stay compact (~median 920 tokens; often 1–4 accepted edits) and transfer across model scales, between Codex↔Claude Code, and to nearby tasks. Elvis (@omarsar0) independently wired it into his orchestrator after initial skepticism and reports a multimodal paper-figure-extraction skill jumping 0.73→0.93 (+20 pts), arguing the same loop can self-improve skills, tool use, context engineering, evals, and harnesses. Directly actionable for Grok Bot / specialist-bot skill libraries: treat skills as versioned, validated trainable adapters—not one-shot prompts.
